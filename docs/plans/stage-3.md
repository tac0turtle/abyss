## 0. Goal, decisions and non-goals

Stage 3 turns abyss from a developer build into something a person can download, run and use with assistive technology. It has four tracks:

- **A. App Sandbox:** the bundle runs sandboxed, and its files move into the container.
- **B. Notifications:** banners for new messages, click-through to the chat, a Dock badge, and their removal on read and on logout.
- **C. Accessibility:** a full VoiceOver pass over every screen, keyboard reachability, and the system display preferences.
- **D. Signing and distribution:** Developer ID signing, the hardened runtime, notarization, a notarized DMG, and the switch to the data protection keychain.

### Decisions (owner, 2026-11-19)

- **D1. Not enrolled in the Apple Developer Program.** Track D is planned in full but blocked until enrollment. Tracks A to C are ordered first, and each is built to work on an ad-hoc-signed bundle. Where ad-hoc signing may not be enough, a spike (task 0) settles it before the design depends on it.
- **D2. Direct download only.** Developer ID and a notarized DMG; no Mac App Store. The sandbox is still adopted, as defence in depth for a client that parses untrusted network input, though the store doesn't require it.
- **D3. Notifications show the sender only by default.** The banner names the chat (and the sender, in a group) and says "New message". D10 removes the opt-in to show message text.
- **D4. A full VoiceOver pass.** Every screen gets roles, labels and keyboard reachability in Stage 3, including settings and folder editing.
- **D5. Closing the window keeps abyss running.** The connection stays up and notifications keep arriving. Cmd+Q is the way to quit (section 3.4).
- **D6. Mentions notify in muted chats**, as Telegram does by default: a mention is addressed to the user.
- **D7. No updater in Stage 3.** Whether to add one (Sparkle 2 with EdDSA-signed appcasts) is decided before the first public DMG.
- **D8. Account-wide notification settings are honoured, read-only.** `account.getNotifySettings` for users and for groups at bootstrap, then `updateNotifySettings` for those scopes (section 3.2).
- **D9. No text-size setting in v1**, unless the VoiceOver pass shows one is needed.

Decided 2026-11-20, after review round 3. Each of the first three rounds found new P0s in notification text removal and catch-up counting, so the owner cut scope:

- **D10. Banners never contain message text.** There is no preview setting. A banner says who wrote and that something arrived: "New message" or "N new messages". A banner left behind after a read or a deletion therefore discloses no content, so removing banners on read and on deletion is best-effort tidying, not a privacy guarantee. Removing all banners on logout stays a guarantee, because banners still name chats and senders. Message text in banners can come back in a later stage, with its own plan.
- **D11. Catch-up posts one generic banner.** After a sleep, a reconnect or a gap, core no longer counts messages per chat. Once the reconcile after the catch-up has settled, it compares the number of unread non-muted chats (the Dock badge's count) with the count before the catch-up. If the new count is higher, it posts one banner: "New messages while you were away". The chat list shows the details. The decision uses only server state after the reconcile, so mute, read and ordering need no catch-up-specific handling.
- **D12. The 5-minute light refresh also runs while the window is hidden**, because closing the window keeps abyss running (D5). This catches silent gaps (S1 §14, risk 7) without waiting for the window to come back.

### Non-goals

- **Push notifications (APNs).** Notifications arrive only while abyss runs and holds its connection. Telegram's push needs `account.registerDevice` with a token the server can deliver to. A third-party APNs path needs its own push service, which is out of v1.
- **Mac App Store builds**, their provisioning, and App Review.
- **An auto-updater** (D7).
- **Per-chat notification editing.** abyss reads the server's mute state and never writes it (`account.updateNotifySettings` is not called). Muting from abyss is a follow-up.
- **Notification sounds** beyond the system default, and inline reply from the banner.
- **Images in banners.** Media is Stage 4.

## 1. Invariants this design keeps

1. **`abyss-core` has no GPUI dependency.** Deciding which events notify, and what a banner may contain, lives in core. Delivering it through `UNUserNotificationCenter` lives in the app.
2. **Generations and account epochs** (S1 §1, events.rs). A notification carries the account epoch it was made in. A click whose epoch is no longer current is ignored, so a banner from a signed-out account never opens anything.
3. **Server evidence only for counts** (S2 §17.6.1). The Dock badge and catch-up summary use the number of unread non-muted chats in the bounded dialog list. They use confirmed unread state. The chat list also applies a temporary overlay while a read is pending.
4. **No plaintext in logs** (S1 §11). Notification text, titles and chat ids are never logged.
5. **Paths are never logged**, and the storage threat model of `storage.rs` stands. Only the root changes (track A).
6. **Secrets stay out of accessibility.** `PasswordInput` already returns bullets to IME and accessibility (S1 §13, task 8). Stage 3 keeps that for AccessKit nodes, and brings the `api_hash` field and the login code under the same rule (S1 follow-up at line 827). The login code field keeps its digit filter, length bound and submit, and draws the digits, but the AccessKit node is a secure field whose text run is one bullet per digit, and the platform's text services read bullets.

## 2. Track A: App Sandbox

### 2.1 Entitlements

`assets/macos/abyss.entitlements`, applied by `scripts/bundle.sh` with `codesign --entitlements`:

- `com.apple.security.app-sandbox`
- `com.apple.security.network.client`, for MTProto over TCP.

Nothing else. No file access, no network server, no camera or microphone, no Apple Events. The only URL abyss opens (`https://my.telegram.org/apps`) goes through `NSWorkspace`, which works sandboxed. The clipboard needs no entitlement.

Ad-hoc signing can carry entitlements, so the sandbox lands before Developer ID (D1). Task 0 confirms this on the current macOS.

### 2.2 The storage root

Today `storage.rs` builds `<home>/Library/Application Support/dev.abyss` from `getpwuid_r`, which is the real home. Inside the sandbox that path is denied: the writable Application Support is the container's, `~/Library/Containers/dev.abyss/Data/Library/Application Support`. `libc` stays a dependency for `getuid` and the small-file open flags.

- The root comes from `NSFileManager URLsForDirectory:NSApplicationSupportDirectory inDomains:NSUserDomainMask`. It returns the container path when sandboxed and the real path when not. `HOME` is still ignored, because Foundation resolves this through the user database and the container, not the environment. Task 0 checks this with `HOME` set to a decoy.
- `storage::app_dir()` (the single root from colourways task 2) is the only caller, so the cache, `theme`, `colourway` and `preferences` files move together.
- `prepare`'s checks (0700, no symlinks, ours, ACLs stripped) apply unchanged below the new root.
- **No migration** (abyss is prerelease). Files under the real Application Support are left where they are.

**Two regimes.** `cargo dev` and `cargo run` run the bare binary and keep the real path. The sandboxed bundle uses the container. Each has its own files, session, cache key and logout state. Each needs its own sign-in. If a cache key has no database next to it, `Cache::open` creates a new cache.

### 2.3 Keychain under the sandbox

A sandboxed app keeps access to its own login keychain items. Ad-hoc signing still changes the signature on every rebuild, so the ACL prompts (S1 §14, risk 3) stay until track D. Task 0 confirms that the existing `KeychainLocation::File` items read and write from the sandboxed bundle.

The login keychain is shared. The bundle uses services under `dev.abyss.bundle` and the bare binary uses `dev.abyss.bare`. The bundle identifier selects the namespace. A fresh manifest follows the storage preference, which defaults to local, and a fresh local manifest never reads the Keychain. A manifest that is missing while the preference says Keychain is recreated pointing at the Keychain, which adopts that namespace's existing items. That is a deliberate recovery, not an import: in Keychain mode the Keychain is the store of record, and its namespace (`dev.abyss.bundle` or `dev.abyss.bare`) belongs to one installation regime and one user, so the items are this installation's own. The alternative, an installation-specific Keychain identity, would add a second durable id whose loss orphans the items, for no isolation the namespaces don't already give. Switching storage still moves secrets within the same installation under its root lock.

**Found in task 0 (macOS 27.2.1, ad hoc):**
- **Keychain:** the spike added, read, updated and deleted items from the sandboxed bundle with no prompt. The items landed in the user's real login keychain.
- **Storage root:** the sandbox overwrites `HOME` and `CFFIXED_USER_HOME` with the container path, while `getpwuid_r` still returns the real home. The old root would therefore have failed in the bundle, which confirms the Foundation root.
- **`HOME` and the Keychain:** Security.framework, unlike Foundation, honours `HOME`. An unsandboxed run with a decoy `HOME` hung on a SecurityAgent dialog at its first keychain add. Dev runs must keep the real `HOME`.

### 2.4 Fake runs

`--fake` runs are dev runs. They stay unsandboxed and keep `$TMPDIR/dev.abyss.fake`. Their theme and colourway files still go to the real app directory, because `app_dir()` ignores `--fake`; this is existing behaviour and is unchanged. A bundle never enables the `fake` feature (`bundle.sh`), so the fake paths never meet the container.

## 3. Track B: notifications

### 3.1 What notifies (core)

Core emits a new event, `Event::Notify(Notice)`, separate from `ChatBumped`. `ChatBumped` also fires for edits, replays and outgoing messages, and the UI must not infer from it.

A message produces a `Notice` only if all of these hold:

1. It arrived as a **live update**: not a history page, not a cache read, not a reconcile.
2. It is **incoming**: not `out`, and not a service message abyss doesn't render.
3. It is **not silent** (`message.silent`).
4. Its chat is **not muted** at the clock (`ChatSummary::muted_at`), or the message **mentions the user** (`message.mentioned`; D6). For a chat without its own mute setting, the account-wide setting for its kind applies (section 3.2).
5. It is in **v1 scope**: a private chat, a group or a forum topic. Broadcasts are already excluded.
6. It is **fresh**: its date is within `NOTIFY_FRESHNESS` (5 minutes) of the clock.

**Catch-up.** After sleep, a reconnect, or "difference too long", the server can replay messages in bulk. While core is applying a difference or a rebuild's reconcile, it holds individual notices. Core records the unread non-muted chat count before the catch-up and compares it after the replay and reconcile finish. A higher count emits one `Notice::Summary` (D11). Startup establishes the initial count. A rebuild waits for its bootstrap snapshots and the resumed difference. Mapped replay updates and known gaps request a reconcile before the catch-up checkpoint. Socket updates buffered during an ordinary light refresh keep their live eligibility.

**The update feed and gaps.**

- **Replay and checkpoints.** The feed passes socket batches and difference replies to the pinned grammers `MessageBoxes` as shipped. It observes signals after the duplicate-sequence check. A supported channel hint marks its batch as catch-up before mapping. The feed emits `CatchUpGap` when a grammers `Gap`, a supported channel hint or incomplete recovery requires a reconcile, then `CatchUpEnded`, then the checkpoint. An idle deadline alone causes neither a purge nor a reconcile.
- **Incomplete recovery.** The feed keeps bounded evidence of Common updates and channel `pts` held by grammers. The Common evidence includes short updates and RPC results. The feed checks whether replay covers those effects and the history updates in a sequence-rejected envelope. It also compares raw account reply history updates with the returned batch, including channel messages, edits and deletions. A missing effect invalidates its chat when known, or all history for an unscoped loss. Channel hints, too-long replies, final channel replies containing ordered history changes, and channel difference failures can also invalidate the affected supported chat. An account reset, too-long account reply or abandoned difference invalidates all history.
- **Invalidation order.** A batch's invalidations follow its mapped items. The actor clears the affected windows and any earlier messages buffered for them. The feed drops later message inserts and edits for invalidated scopes until that replay ends, while passing send acknowledgments and other effects. A later replay slice alone cannot establish a contiguous background tail. The reconcile fetches the open tail, and background threads fetch history on open.
- **Reset and budget.** An accepted `updatePtsChanged` abandons the old boxes and any pending channel recovery, fetches a new baseline with `getState`, and reconciles. The feed uses the same path when a difference exceeds the `MAX_DIALOGS` channel budget and grammers cannot evict enough least recently active channels. Evicting a channel with unresolved gap evidence invalidates its history. Checkpoints carry at most `MAX_DIALOGS` channels. The feed keeps send acknowledgments from abandoned batches. It forgets channels identified as broadcasts by response peers, an explicit post or the session, excludes their positions from checkpoints, and skips their history invalidations and channel recoveries.
- **Durable invalidation.** The encrypted cache worker commits a chat or account quarantine marker before deleting the affected message rows, including all forum threads of a stale chat. It removes that marker in the same transaction as the deletion. The actor invalidates retained windows and their in-flight history replies. Quarantined history reads return misses and the dialog list remains available. When a purge fails, the actor holds the in-memory checkpoint and retries at the next baseline. Cache open retries persisted quarantines and keeps serving misses for affected history if the retry fails. A failed marker write disables all cached history reads for the session.
- **Gap snapshots.** A gap during snapshots schedules a trailing refresh. A gap while live and idle starts the refresh immediately. The refresh reads both account mute scopes, waits for an older dialogs page before requesting its own first page, and waits for an older history load before requesting the attached, unfenced tail. Only successfully applied required results satisfy the reconcile. A failed or discarded required snapshot rebuilds from the last accepted checkpoint. The requirement survives retirement so the replacement bootstrap must also succeed before accepting a checkpoint.
- **Request and batch bounds.** Each feed RPC has a 30 s deadline. A timeout retires the instance, so stalled requests cannot accumulate in its runner. The feed caps messages, updates and peer directories, caches peer information for later channel access, and rejects a too-long channel reply without a dialog `pts` because the grammers adapter panics on it.
- **Hidden window.** The five-minute refresh runs whether the window is active, inactive or hidden (D12). A known gap triggers a reconcile in every state. The next periodic refresh checks dialogs and the open tail for undetected changes.

**Rate limit.** At most one `Notice` per chat per `NOTIFY_COALESCE` (2 s). Core keeps a bounded set of contributors by message id and topic. A read removes the messages its pointer covers, and a confirmed deletion removes the matching ids. A notice carries the surviving count and uses the newest surviving message as its target. A peer mute lookup can delay delivery. If a notice goes out while a lookup is pending, its delivery time starts the earliest possible next window for that chat's deferred candidates.

Pending contributors survive same-account rebuilds, even when the feed has already committed their checkpoint. Both tail merge and replacement remove pending and deferred contributors missing from the authoritative id range of the same thread. When core queues a tail, it records the highest contributor id alongside the window's newest id. A page that starts at the server's newest available message accounts for missing ids up to that request-time bound, including when the window was cleared and cache history is unavailable. The oldest returned id bounds a partial page, and an empty partial page proves no deletions. A contributor above the request and response bounds can have arrived during the fetch and stays queued. A bounded recent set of chat and message ids suppresses duplicate socket or catch-up updates. Account teardown clears both sets.

**`Notice` contents:**
- `chat: ChatId`, `topic: Option<TopicId>`, `msg: MsgId`;
- `chat_title`, sanitized via `sanitize::display_name`, as the chat list shows it;
- `sender`, in groups only, sanitized the same way;
- `count: u32`.

A `Notice` has no message text (D10). Core never puts message content in a notification event, so it can never reach the app or Notification Center.

### 3.2 Mute state, live

Notifications make the S2 follow-up "live `updateNotifySettings` isn't applied to folder mute rules" a correctness bug: a chat muted on the phone would keep notifying here until the next dialogs page. Stage 3 applies `updateNotifySettings` for peers (`notifyPeer`) live, with the same crossing-response guard folder moves use (folders.md, part A): the mute field gets a per-field stamp. `notifyForumTopic` is ignored, because per-topic settings stay out of scope (S2 §0).

**Account-wide scopes (D8).** At bootstrap and during known-gap reconciliation, core reads `account.getNotifySettings` for `inputNotifyUsers` (private chats) and `inputNotifyChats` (groups and forums) through the shared read retry path. Live `updateNotifySettings` for `notifyUsers` and `notifyChats` replaces them. `notifyBroadcasts` is ignored, because channels are out of v1.
- A chat's own `mute_until` wins when the server set one. Otherwise the scope's `mute_until` for its kind applies. Telegram resolves it the same way, and `peerNotifySettings` flags which fields are set.
- The scope settings live in memory. Core applies live settings buffered during the reads before deciding the D11 summary. Held message notices recheck the effective mute at delivery, preserving the mention exemption.
- Session revocation and migration go through the lifecycle handler before a settings read can finish bootstrap. A failed scope read during gap reconciliation holds the checkpoint and triggers the usual rebuild. Outside gap reconciliation, a failed bootstrap read uses an unmuted default and logs a warning without details.
- Peer mute evidence starts empty for each account. Retirement, a known gap or a stale-history signal clears that evidence as soon as the actor handles it. Fresh dialog snapshots and live peer settings confirm the peers they cover. A lookup dispatched before the cutoff is retried if candidates are still waiting. Cached and provisional rows require fresh evidence before their mute settings can govern ordinary notices.
- For an unknown peer setting, core defers ordinary candidates, including pending contributors that have reached delivery, and reads `account.getNotifySettings` through the shared read retry path. The queue holds at most 32 peers and only one peer lookup runs at a time. A successful empty setting confirms inheritance. The same field stamp guard protects the result from crossing a live change or a newer dialog snapshot. If the queue is full for a new peer, the candidate budget is exhausted, or the setting cannot be confirmed, core drops the ordinary candidates affected by that limit. Mentions use their usual mute exemption.
- Chat-list mute marks and folder `exclude_muted` rules use the same resolved mute as notices once the peer's setting is confirmed. Provisional rows can still show their previous setting until refreshed.

### 3.3 Delivery (app)

- **Framework:** `UNUserNotificationCenter` through `objc2-user-notifications`, pinned at the version that matches the `objc2` already in the tree.
- **Only in a bundle.** `UNUserNotificationCenter currentNotificationCenter` throws for a process with no bundle identifier, which is how `cargo run` launches. The app checks `NSBundle.mainBundle.bundleIdentifier == "dev.abyss"` and that the executable runs from inside a `.app` before touching the center. Otherwise notifications are off and a single INFO line says why. **The guard is mandatory** (task 0): without a bundle, `currentNotificationCenter` aborts the process (exit 134). The exception is raised inside `dispatch_once`, and `objc2::exception::catch` cannot catch it. A test proves the unbundled test process never reaches the center.
- **Authorization** is requested once an account is signed in, not at launch, whether the sign-in is new or a restored session (a quit between the sign-in and the system's reply must not leave the person unable to be asked). While the system reports not determined, Settings also offers "Enable notifications", which asks the same way: alert, badge and sound. The control and its handler need the same active delivery epoch as the automatic prompt, so Welcome, an ended account and a removal-only center (whose epoch seed failed) never ask. A refusal is remembered by the system. The completion handler can wait on the person indefinitely, so nothing blocks on it, and the state stays unknown until it arrives. Settings shows the current state and links to System Settings, Notifications (an `x-apple.systempreferences:` URL, the second URL abyss may open; roadmap "v1 scope" is amended).
- **Suppression:** no banner when the window is key and the notice's thread is the one on screen. When the window is key but showing another chat, the banner shows. A thread is on screen only while no modal overlay covers the pane (section 3.4, "A modal overlay covers the pane"): behind Settings or the logout confirmation, the banner shows.
- **Spoilers:** a hidden spoiler never reaches a chat-list preview, a reply's quote or an accessibility label as itself (banners carry no text, D10). The preview, the reply's quote and every excerpt of the message (the sidebar row's label, the quote's label) use `RichText::excerpt`, which replaces each spoiler with "Hidden spoiler" (core, `rich_text.rs`), even once the message was revealed: revealing is an act in one place, on the message, and does not unredact copies of it elsewhere. The message's own accessibility label is the exception that follows the screen: it speaks "Hidden spoiler" until the user reveals that range, then the revealed text, because the text is then on screen. The inventory and the native scene `rich_actions` check both. Spoiler ranges are kept independently of the formatting budget: an over-budget text, entity list or link set loses its formatting and links, never its spoilers. A range off a character boundary widens to it. When the spoilers themselves can't be established (more than 256, or a negative offset or length) the whole text is one spoiler, redacted rather than shown. At the wire the count is of the raw spoiler entities, before any is discarded or skipped: empty and out-of-range ones count too, so a bounded prefix can never hide a valid spoiler that a later one would have.
- **Content (D10):** a message banner names the chat and, in a group, the sender. The body is "New message" or "N new messages". `threadIdentifier` is the chat id, so Notification Center groups by chat. A catch-up banner says "New messages while you were away" and activates abyss when clicked.
- **`userInfo`** carries only the account epoch, the chat id and the topic id, as integers. No titles and no text.
- **Click:** the delegate's response handler validates `userInfo` (types, ranges, current epoch) and posts an app action that brings the window forward and opens that chat or topic. Anything invalid just activates the window, and so does a click on a banner from an earlier launch, whose epoch can never be current. Core notifies about chats and forums the dialogs list doesn't hold yet (a new message doesn't list one), so the app keeps the chat, topic and title of each banner it delivered in this epoch (at most 128, the oldest forgotten first, cleared when the account ends). The evidence, like the tracked notification, is committed only when the system accepts the delivery request: a failed request evicts nothing, and a banner read or deleted while its request is still outstanding is removed again and commits nothing. At most 64 delivery calls wait for the system at once, messages and catch-up summaries alike. A call counts until its own answer arrives: a read or a deletion removes the banner (the request stays, marked covered, and commits nothing) but does not free its slot. The cap applies at admission: past it a new banner is not handed over at all (with that many unanswered the system is not keeping up), so a request that was handed over never loses its evidence, and a late success is always tracked. Every click needs that evidence, for a listed chat or topic as much as an unlisted one. The evidence is a committed target or, because the handoff serves a click before the answer that confirms its own banner, a request still outstanding for that thread in this epoch and not covered by a read or a deletion; the outstanding request backs the click and commits nothing. The evidence is bounded, so a click on a banner whose evidence was forgotten (more than 128 chats delivered since) only activates the window, as does a payload the app did not deliver and a malformed one. A chat the dialogs list holds is authoritative: it opens from its own row, a topic needs it to be a forum, and a stand-in never replaces it. A chat the list does not hold opens from a stand-in summary built from the evidence (the title, the peer kind, a forum by its topic). The stand-in is never sendable, whatever the kind, because a group may restrict posting and only core's summary knows; it is read-only until the list holds the real one, which replaces it. It lives in the chat shell's one provisional slot, outside the sidebar's 1,000-chat cap, so a full sidebar still opens an evidenced banner. The slot holds one chat, and a later click replaces it once the switch is admitted: a click core refuses (its queue is full, too many drafts) leaves the open chat and its slot as they were. A topic banner for a different forum opens the list and the topic with one `OpenForumTopic` command. Refusal leaves the pane, provisional slot and core's shown forum in place. The logout confirmation is modal: while it is open a click only activates the window, so focus stays in it and nothing navigates behind it. A click closes the Settings panel and any open menu first, so nothing else owns focus when the pane moves.
- **Removal:**
  - a read here or on another device attempts to remove delivered notifications covered by the read pointer. A dialogs or topics snapshot's pointers count too, for banners still waiting for the system's answer as for committed ones; while the launch's enumeration is outstanding, every positive pointer of a snapshot, a chat's as much as a topic's, also joins the early floors: the shell holds only the shown forum's topics, and a later reset can drop a chat from the list before the enumeration returns its old banner.
  - a confirmed deletion attempts to remove matching banners by their stored identifiers. This includes deletions confirmed by a tail reconcile and deletion updates for messages outside core's windows. Account-wide deletion ids only match private chats and basic groups. The launch's enumeration of delivered notifications is asynchronous, so a deletion or a read can arrive before it, for a chat or topic no list holds: until it completes the app keeps at most 1,024 deleted ids and at most 1,024 read floors (the highest pointer per chat or topic) and applies them to what it reports. Past either bound the evidence is incomplete, and every enumerated notification the launch did not deliver is removed instead (such a banner can only activate the window anyway). The completions the app cannot repeat are sent reliably: the enumeration's result, the system's answers to delivery requests, the settings read and the authorization reply (a lost reply would leave the prompt in flight and hide "Enable notifications" until restart). They wait for room in the app's event queue, which holds every outstanding answer the cap allows. A click arrives on the main thread, which never waits, so it has its own small queue that drops its oldest click to keep the latest and is served before the event queue: a burst of delivery answers cannot drop it;
  - on logout and on account switch, the durable logout marker records whether delivered and pending notifications need removal. With a center, core waits for confirmation before it erases the session. A failed confirmation keeps the marker and the logout can be retried. If epoch generation fails, the bundle keeps a center for removal and disables delivery and click-through.
  - a process without a center still erases the session and cache. Only after erasure does it change the marker to record notification cleanup alone. The user can sign in again in that process. Old banners can remain in Notification Center until a capable launch. That launch must confirm removal before it loads a session or cache. A failed confirmation blocks startup and Retry checks again. The bare binary has a separate account and Keychain namespace, so logging out there does not log out the bundle's account.
- **Dock badge:** the number of unread non-muted chats from confirmed unread state, displayed up to "99+". On by default, with a setting to turn it off (not offered on a removal-only center, which never badges). It is cleared on logout.

### 3.4 Closing the window

Today the close button and Cmd+W run the S1 shutdown (`shell/mod.rs:146`, `on_window_should_close`), and the app quits once no window is left (`main.rs:27`). Under D5:

- **Close hides.** While signed in, the close button and Cmd+W hide the app (`App::hide`) and return `false` from `on_window_should_close`, so the window, `Root` and core stay alive. On the Welcome, sign-in and error screens there is nothing to keep running, so closing still quits as today.
- **Reopening.** A Dock click, a notification click and Cmd+Tab bring the window back, with the state it was hidden in. Notification clicks and in-app paths use `cx.activate(true)`, which un-hides with the state intact (task 0). GPUI's `App::on_reopen` fires only when no window is visible, so it is a fallback for the Dock click, not the main path. Whether a Dock click un-hides a hidden abyss is still an owner check (task 0).
- **Quitting.** Cmd+Q and the app menu's "Quit abyss" run the existing S1 shutdown ("Closing…", the exit drain, the 200 ms quit budget). Logout still ends at the Welcome screen, as it does today.
  - **The closing overlay is a modal dialog.** "Closing…" is a dialog named by its text, with a polite status. The two cards that follow it ("Couldn't confirm the session was saved", "Logout incomplete") are dialogs named by their heading, with the detail as an alert and a Quit button. The overlay hides the window's body from assistive technology, so it must be a node of its own, and it owns focus (`Root::overlay_focus` checks it first): while it shows, Tab and Shift+Tab stay in it, on the dialog while core is closing and on Quit once a card asks.
  - **A modal overlay covers the pane.** The closing overlay, Settings and the logout confirmation are near-opaque veils over the whole window, but the chat pane keeps painting behind them. One predicate, `Session::pane_covered`, says so, and two things use it. The frame observer (`ChatShell::frame_seen`) treats a covered pane like an inactive window: no `MarkRead`, and `ViewingTail(None)` for a tail that was watched. The first frame painted uncovered reports both again, since neither was recorded as sent. The withdrawal of a watched tail is owned by the transition to covered, not by the frame retry: it has its own backoff (500 ms doubling to 8 s, never giving up while the cover stays), so loads or read marks that exhausted the frame retry cannot strand it. A later uncover supersedes it The banner suppression above uses the same predicate. A context menu covers a few rows and leaves the transcript readable, so it does not count. Unread state and the banner therefore never claim messages as seen that nobody could see.
  - **An overlay owns focus until it closes.** Core's replies and timers move the auth screen on by themselves (a code prompt after a phone number, a flood wait ending), and an event can change the pane (a topic removed). While any overlay shows (the closing overlay, Settings, the logout prompt, a menu: the same order as `Root::overlay_focus`), such a move leaves focus where it is, so typing cannot reach a field behind the modal. The session notes that focus is owed, and the close of the last overlay completes it: the current auth field, or the pane's focus target (the composer only while the pane renders one; a read-only chat, a closed topic, a stand-in and a topic list focus the pane itself, `Session::pane_focus_target`, shared with every pane change). An overlay belongs to the screen it was opened on: the context menu closes when the screen leaves `SignedIn`, and the logout confirmation when it leaves `SignedIn` or `Done` (a revoked session, a logout starting). They close through the normal paths, so their focus is released and owed focus is paid, and the confirmation is only drawn, and only owns Tab, while the screen allows it.
  - **Quit closes what is open first.** `Root::request_quit` closes Settings, the logout prompt and any menu before it starts shutdown, and Settings is never drawn beside the overlay. Nothing is left behind the overlay to take focus or to be read.
  - **The key reaches the window.** A global action listener runs inside the update of the window that dispatched the action, which has that window leased. The listeners for Quit, Cmd+W and Cmd+comma used to update the window from there, which failed with "window not found": Quit then took the "window gone" branch and quit at once, skipping all of the above, Cmd+W quit instead of hiding, and Cmd+comma did nothing. Each route now runs once the dispatch is over (`route_actions`).
  - **Limit: an OS-initiated quit skips the overlay.** Quit from a hidden app's Dock menu, Cmd+Tab then Q, and a logout or shutdown call `NSApplication terminate:`. The pinned `gpui_macos` implements `applicationWillTerminate:` and not `applicationShouldTerminate:`, and `on_app_quit` cannot cancel, so no hook can route this through `request_quit`, and abyss does not patch GPUI. The quit callback (`quit_signals`) asks core to stop, and its future waits for core's ack inside GPUI's 200 ms budget. Core normally saves within that, so the session is kept; if it does not, GPUI exits at 200 ms and the cache is protected by the exit hook (section 13 of S1). The user sees no "Closing…" and no card on this path, and a save that could not be confirmed is not reported. Logout is unaffected: its marker is written before anything is deleted (A1).
- **Window activation.** The light refresh on window activation (S1 §14, risk 7) fires when the window comes back. Suppression (section 3.3) treats a hidden window as not key.
- Task 0 checks that GPUI keeps rendering correctly after `hide` and reopen, and that a window hidden this way survives sleep and wake.

## 4. Track C: accessibility

### 4.1 Framework

The pinned GPUI carries AccessKit (`Z/crates/gpui/src/window/a11y.rs`, `accesskit_macos` 0.26). Elements take a `Role`, a label, a value, a toggled state and accessible actions (`Z/crates/gpui/examples/a11y.rs`). `Window::debug_a11y_tree_json` serializes the last tree sent to the platform, which makes the tree testable without VoiceOver.

Task 0 checks three things against abyss's own window, not the example: VoiceOver reads it; focus follows GPUI's focus handles; and the custom text inputs (`input.rs`, the composer, `PasswordInput`) can expose text, selection and caret position to AccessKit at all. If the last point fails, the inputs fall back to a labelled `TextInput` role whose value is set from the buffer, and the gap is filed upstream.

**Found in task 4:**
- **Text inputs work.** The pinned GPUI exposes text, caret and selection through synthetic `TextRun` nodes, so the fallback isn't needed.
- **The tree tests use AppKit directly.** GPUI's headless test windows don't activate AccessKit, and `debug_a11y_tree_json` leaves out selection, live state and bounds. The tests therefore activate the native AppKit adapter and query AppKit itself (`crates/app/src/native_a11y.rs`).

Controls in scrolling containers therefore register their activation directly (`a11y::on_activate`, `on_activate_in`); see the inventory's Activation paragraph.

## 8. Risks

- **Ad-hoc limits.** If task 0 finds that notifications or the sandbox need a Developer ID signature, tracks A and B move behind D1, and Stage 3 can only ship accessibility before enrollment.
- **AccessKit text inputs.** GPUI's AccessKit support is new. If custom inputs can't expose text and selection, VoiceOver users can type but not review what they typed. That is a known gap until upstream supports it, and is recorded rather than worked around.
- **A notification is a disclosure.** A banner shows on the lock screen and in Notification Center, and macOS keeps it after abyss quits. Banners never carry message text (D10), all banners are removed on logout, and nothing in `userInfo` beyond ids bound this. The system's own "Show previews" setting still applies on top.
- **Catch-up summary.** The number of unread non-muted chats can stay flat even when new messages arrived, for example when an already unread chat receives more messages. Live delivery also has a five-minute freshness window.
- **Peer mute reads after startup or recovery.** An ordinary banner for a peer outside the refreshed dialogs can wait for a settings read. A failed read or a saturated lookup queue can drop the banner. A provisional row can keep its old mute mark and contribute to the catch-up count until refreshed.
- **Cache quarantine write failure.** A read-only database or another storage failure can prevent the quarantine marker from committing. Cached history stays disabled for that session. If the process exits before any retry can write the marker or commit the purge, the next launch may still see the old rows.
- **Upstream grammers message-box limitations (pinned `e61cf85`).**
  - A hint with `pts` overwrites the stored channel position. Recovery can start past the missing range (A43/A65).
  - A final channel reply ends recovery and installs its `pts` before processing `other_updates`. Ordered updates in the body, including deletes and edits, can be treated as duplicates (A44).
  - When only Secondary reaches its deadline, grammers requests the account difference with Common's position. Applying the reply advances Common's `pts` before processing its ordered updates, so Common deletes and edits can be skipped (N50).
  - grammers passes `updatePtsChanged` through unchanged. abyss responds with a fresh `getState` in an empty message box and abandons pending channel work. A transient failure can delay the new baseline (A47/A67).
  - A reorder deadline discards grammers' out-of-order buffer. The public API exposes the same request for an expired buffer and an idle poll. abyss observes `pts` and history identities from socket envelopes and difference replies to detect losses, including updates grammers held or filtered. It cannot recover payloads that were never observed, and finite history evidence can fall back to a broader purge. Missing deletions can leave previously delivered banners visible until a later read or deletion covers them. Undetected gaps remain subject to the periodic dialog and open-tail refresh.
  - Channel scope comes from peer metadata. When an unclassified channel has no access hash, the feed preserves conservative recovery because that channel could be a previously cached supergroup. Known broadcasts are excluded before writing the checkpoint.
- **Notifications only while running.** Without push, nothing arrives after Cmd+Q or a logout. Keeping the app running when the window closes (D5) covers the common case.
- **Hidden but connected.** Under D5 the session stays live with no window on screen, so the Keychain-held session and the open cache stay in memory longer than before. The memory threat model is unchanged: they were already live whenever the window was open.
- **Two storage regimes** make "my history is gone" reports likely between `cargo dev` and the bundle. This is documented in the README, under "Getting started".
- **The provisioning profile** for `keychain-access-groups` (section 5.3) is unverified. If a Developer ID profile can't carry it, the login keychain stays and the S1 §13 note is amended.
- **Outbound connects stalled in task 0.** A new ad-hoc binary's TCP connect hung, both sandboxed with `network.client` and unsandboxed, while `nc` from the shell connected. This is likely a firewall or network filter on the dev machine, and it's unconfirmed. Live checks (task 12) must rule it out for the bundle.
- **The accessibility tree is lazy.** GPUI builds it only once an assistive client attaches, so a VoiceOver-only failure can hide from casual runs. The native test runner from task 4 attaches as that client.
- **GPUI pin.** Accessibility may need a GPUI bump for fixes. A bump goes through the usual diff review and is its own commit.
